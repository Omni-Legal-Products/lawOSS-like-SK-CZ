Vojta Říha

Pamäť, ktorá sa dá vybaviť, meniť a kontrolovať

Granularita a retrieval
Čo

Typovaný záznam

Každý poznatok má typ, scope, krátky description alebo summary a väzby. Lesson nie je obyčajná poznámka.

Prečo

Konvencia časom zlyhá

Keď typ nie je vynútený, pamäť splynie. Agent potom načítava priveľa textu a človek nevie samostatne revidovať poučenia.

Ako

Brány v nástroji

Zmena Truth bez History sa odmietne. L1, L3 a mazanie potrebujú human gate. Vrstvy majú vlastné pravidlá.

LOADrelevantné summary
→
SAVEnový poznatok
→
LEARNnávrh poučenia
→
REVIEW + EVOLVEčlovek rozhodne

Čo zachovávame bez oslabenia

  • summary ako retrieval hook,
  • links medzi poznatkami,
  • Truth a append-only History,
  • L1/L2/L3,
  • samostatný typ lesson,
  • nástrojové write gates.

Čo musí doplniť OKF

  • klientsky a prípadový root,
  • AGENTS bootstrap,
  • scaffold a retrofit,
  • registry verification,
  • práca s reálnymi dokumentmi,
  • portable umiestnenie pri spise.
Marián Čuprík

Priečinok ako fundamentálny operačný systém praxe

Klient, prípady, interoperabilita
Čo

Klientský workspace

Jeden klient alebo subjekt má spoločnú identitu a viac samostatných prípadov. Každý prípad má vlastný stav a pamäť.

Prečo

Inteligencia patrí k dátam

Ak agent otvorí priečinok mimo LAWOSS, stále musí vedieť, čo čítať, čo je pravda a kam smie zapisovať.

Ako

AGENTS ako bootstrap

AGENTS.md je prvý vstup. CLAUDE.md je byte-identický mirror. BRAIN.md je iba regenerovateľný kontext.

ACME s.r.o./ ├── AGENTS.md kanonický vstup ├── CLAUDE.md mirror ├── okf.yaml machine contract ├── client.md potvrdená identita ├── memory/ klientske records ├── findings/ rozpory a návrhy ├── evidence/registry/ dôkazy overenia └── Prípady/ ├── Dodávateľ XY/ │ ├── AGENTS.md │ ├── matter.md │ ├── _STATUS.md │ ├── memory/ │ └── dokumenty... └── Pracovnoprávna vec/ └── vlastný izolovaný L2 kontext

Nový priečinok

Výber rootu -> typ subjektu -> verification -> dry-run -> potvrdenie -> scaffold -> validate.

Existujúci priečinok

Read-only detect -> presný migračný plán -> potvrdenie -> iba chýbajúce artefakty -> report. Originály ostávajú.

Doménová hranica

Workspace je klientsky root

Jeden LAWOSS workspace predstavuje jedného klienta alebo subjekt. V ňom žijú stabilne identifikované prípady. Názov priečinka nie je identita.

Zdroj pravdy

Súbory, nie databáza

SQLite môže držať regenerovateľný snapshot, diagnostiku a technické operácie. Klient, prípady, pravda, história a evidence zostávajú v OKF súboroch.

Poradie práce

Platforma pred pohľadmi

Najprv parser, validator, watcher, návrhy, approval a recoverable writer. Dashboard príde až po overení celého systémového toku.

Tri technické možnosti

Prečo odporúčame spoločný Core

Možnosť A

PR #24 priamo napojiť

Najrýchlejší prototyp, ale zachová legacy parser, matter-only model a slabšie approval a transaction hranice.

Verdikt: nepoužiť priamo ako kanonický základ.

Možnosť B

OKF iba v serveri

Jednoduchšie pre LAWOSS, ale externý Codex, Claude alebo OpenCode by nepoužíval rovnakú implementáciu pravidiel.

Verdikt: zamietnuť pre slabú prenositeľnosť.

Možnosť C

Core + CLI + server adaptér

Jedna implementácia formátu, validácie a zápisových invariantov pre všetky harness-y. LAWOSS pridáva runtime autoritu a UX.

Verdikt: odporúčaný smer.

Z PR #24 zachovať

  • typované records a retrieval summary,
  • Truth a append-only History,
  • L1/L2/L3 a samostatný lesson,
  • marker-scoped projekcie,
  • validácie väzieb, freshness a L3 leakage,
  • behaviorálne testy a deterministický diff.

Pre spoločný Core prepracovať

  • anglický machine contract a klientský root,
  • robustný YAML parser a preservation unknown fields,
  • izoláciu parse chýb po súboroch,
  • approval viazaný na actor, plan hash a manifest,
  • whole-store validation a optimistic concurrency,
  • journal, crash recovery a LAWOSS server adaptér.
Implementačné poradie po odklepe
  1. read-only Core a SK/CZ fixtures,
  2. serverový read model, diagnostika, watcher a eventy,
  3. persisted proposals, approval a recoverable writer,
  4. onboarding, retrofit, migrácia a Basic verification,
  5. agentové tools a až potom dashboard a custom views.

Čo treba potvrdiť pred implementáciou

Najprv kontrakt, potom kód
D1

AGENTS.md ako kanonický bootstrap

CLAUDE.md je mirror, BRAIN.md je odvodený. Toto rozhoduje o prenositeľnosti mimo LAWOSS.

na odklepnutie
D2

Klientsky workspace s viacerými prípadmi

Spoločná identita klienta, izolovaný L2 stav každého prípadu.

na odklepnutie
D3

Anglický machine contract

Jedna perzistenčná schéma. Lokalizácia žije v ľudskom rozhraní.

na odklepnutie
D4

Records ako SSOT, status ako projekcia

Lehota alebo chronologická udalosť nesmie mať dve nezávislé pravdy.

na odklepnutie
D5

Risk-based human gates

Observation môže byť automatická. Identita, lehota, stratégia, L1, L3 a mazanie potrebujú človeka.

na odklepnutie
D6

Jeden plan, validate, approve a apply kontrakt

CLI, agent a LAWOSS nesmú implementovať tri odlišné zápisové protokoly.

na odklepnutie
D7

Runtime approval pre chránené zmeny

AGENTS orientuje, ale neautorizuje. Self-declared approval objekt ani prompt nesmú odomknúť právne významný zápis.

na odklepnutie
D8

PR #24 ako referenčný prototyp

Zachovať koncepty a behaviorálne testy, ale cieľový Core postaviť podľa spoločného kontraktu a app hraníc.

na odklepnutie
D9

Dashboard odložiť za platformu

Najprv Core, read model, watcher, approvals, recovery, onboarding a agentové tools. Dashboard bude neskorší konzument snapshotu.

na odklepnutie

Otvorené, ale neblokuje kontrakt

  • fyzické miesto kancelárskeho brainu,
  • budúce auto-approve nízkorizikového L2,
  • plný lock model pre viac používateľov.

Otvorené a blokuje časť implementácie

  • konkrétni Basic providers pre SK a CZ,
  • prechodné obdobie legacy formátov,
  • pilotná migrácia na jednom súkromnom spise.
