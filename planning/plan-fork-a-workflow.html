Plán: fork, repozitár a spôsob práce

Ako založíme fork LegalWorku, ako budeme štyria fungovať a ako fork udržíme lacný

Stav: návrh na odklep 12. 8. Nadväzuje na ADR 0004 · ADR 0005 Fakty overené 2026-08-10
Tento dokument je vykonávací plán, nie nové rozhodnutie. Cieľ: po odklepnutí na calle 12. 8. je založenie forku mechanická práca na menej než hodinu — a od prvého dňa fungujeme podľa dohodnutých pravidiel.

0Uzavretie otázky „ako forknúť"

Analýza varovala, že klasický fork ruší výhodu upstreamu. ADR 0004 to uzavrel — a rozpor sa zmieruje takto:

  • Varovanie platí pre fork, ktorý prepisuje cudzí kód. Naše zmeny sú nové súbory (SK/CZ locale, vlastné adresáre) + 2 evidované miesta brandingu.
  • opencode jadro neforkujeme — LegalWork ho drží ako pinnutú závislosť a my to zdedíme nezmenené.
  • Divergenciu ohraničuje disciplína: pridávaj súbory + PATCHES.md + upstream-first.
Overené cez GitHub API 2026-08-10: najnovší release upstreamu je stále v0.1.13 (2026-08-04) a účet s menom lawoss podľa API neexistuje — meno je pravdepodobne voľné, definitívne sa potvrdí pri zakladaní organizácie.

1Deň D — založenie repozitára

1 · org lawoss→ 2 · presun koordinačného repa→ 3 · Fork legalworku→ 4 · main na tagu v0.1.13→ 5 · ochrana main + upstream remote→ 6 · PATCHES.md · AGENTS.md · NOTICE→ 7 · rebranding + sk/cs locale
Poradie je záväzné: organizácia pred forkom (ADR 0005). Fork výhradne cez tlačidlo Fork — inak nefunguje Sync fork ani väzba na upstream. V deň D netreba: podpisové tajomstvá, ladenie CI, UI zmeny.
Nultý krok ešte pred forkom: MCP konektory (judikatúra + Slov-Lex) rozdať kolegom hneď ako návod so screenshotmi — LegalWork ich pridáva cez Settings UI.

3Pamäť projektu a implementácia

Rozhodnutia tu, kód tam. ADR a specy sa do forku nepresúvajú — fork nesie AGENTS.md (pravidlá pre ľudí aj AI), PATCHES.md a implementačnú stopu v issues/PR.
💡 nápad→ 📝 spec + navrhy.md→ ✅ odklep na calle→ 🎫 issue vo forku→ 🌿 feat/* vetva→ 🔀 PR + review + CI→ 📦 merge → roadmapa

Dvojjurisdikčnosť 🇸🇰🇨🇿 — os štruktúry, nie preklad na konci

lawoss/                ← naša doména (zelená zóna)
├── okf/       sk/ · cz/        šablóny spisov, lehoty — CZ vlastní VŘ
├── prompts/   common/ · sk/ · cz/
├── mcp/       sk.json · cz.json
└── skills/    per-jurisdikcia tam, kde treba

sk.ts a cs.ts vznikajú súčasne (MČ + VŘ) · glosár dostane CZ stĺpec · štruktúra drží doménu prenosnú (funguje aj v čistom opencode / Claude Code).

4Synchronizácia s upstreamom

🔔 ich release→ fetch --tags + changelog→ vetva sync/upstream-vX.Y.Z→ merge tagu (nie main)→ konflikty podľa PATCHES.md→ CI + smoke test→ PR → release v*-lawoss.1

Šablóna PATCHES.md — žiadny zásah do upstream súboru bez riadku tu; pri merge konflikte je tabuľka checklist.

Kto rieši konflikty (návrh): sync vlastní MČ s AI asistenciou · konflikt v zásahu rieši vlastník zásahu · ak konflikt presahuje kapacitu, zásah radšej zahodiť a nahradiť novým súborom alebo upstream PR.
Upstream-first: čo nie je SK/CZ doména, ponúknuť najprv upstreamu — každý prijatý PR zmenšuje náš diff. Lokalizačný PR podať skoro, nech vzťah s upstreamom existuje skôr, než niečo budeme potrebovať my.

5Architektúra addonov — tri zóny

🟢 Naše adresáre

lawoss/** · sk.ts, cs.ts · naša dokumentácia. Voľná ruka — nové súbory sa s upstreamom nikdy nezrazia. ~90 % našej práce.

🟡 Evidované zásahy

branding (2 miesta) · ikony · i18n index. Každý zásah = riadok v PATCHES.md + vlastník. Cieľ: pod ~10 riadkov.

🔴 Zakázaná zóna

AGPL plugin legalmemory · hard-coded extension registry · bump opencodeVersion · prepis histórie. Zmena len cez nový ADR.

Rozšírenia opencode sú konfiguračné (MCP, skills, agenti, pluginy) — naša doména sa pripája registráciou, nie zásahom do jadra. Celý scope V1 sa zmestí do zelenej zóny; ak by ju niečo muselo opustiť, je to signál na rozpravu, nie na tichý zásah.
